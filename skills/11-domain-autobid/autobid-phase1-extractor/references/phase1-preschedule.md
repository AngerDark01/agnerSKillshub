# 前附表 / preschedule 处理

## 定义

这是第一阶段里专门处理前附表的任务指南。

本文档负责定义：

- 这项任务要关注哪些输入文件
- 这项任务要产出什么结果
- 需要调用哪些底层工具
- 遇到查表位置不稳定时如何处理
- 具体执行步骤和经验约束

## 输入与关注文件

执行 `preschedule` 时，优先关注这些输入：

- 当前活跃工作区的 `input/files/<项目目录>/`
  这里通常能找到这一标包的招标文件、招标公告、投标须知、货物清单等原始文件
- 招标文件正文
  前附表主表通常在这里
- 招标公告
  有些项目的招标公告是招标文件中的一部分；有些项目会单独提供一份招标公告，遇到独立文件时应把它当成正式来源之一
- 招标附件
  包括附表一、货物清单、限价表、交货信息表等，很多字段实际藏在附件中
- 补充投标须知
  可能是单独的 xlsx 或 docx，用于补前附表未覆盖但仍要求投标人关注的条款

这里优先读取当前 workspace 的项目文件，不默认去 `Data/` 找值；`Data/` 更适合放公共模板和企业资料，不适合作为前附表字段值的首选来源。

## 任务隔离与渐进读取

- `preschedule` 默认由独立 subagent / 独立上下文执行
- 开工时先只读：
  - `../SKILL.md`
  - 当前文档 `phase1-preschedule.md`
- 只有在遇到“字段位置不稳定 / 引用链未解开 / 需要跨表回退查值”时，才继续读取：
  - `phase1-preschedule-field-lookup.md`
- 只有在已经确认要做某个机械动作时，才继续读取对应的 `base-tools`
- 不要在 `preschedule` 任务里预读：
  - `phase1-qualifications.md`
  - `phase1-scoring.md`
  - 任何 `phase2` 文档
- 除当前正在处理的条款外，不得一次性通读招标公告全文、全部附件或全部 xlsx；只有当前步骤明确触发时，才继续读取对应范围
- `preschedule` 结束后，只把结构化结果、产物路径和未决项回写到 workspace；后续商务文件如需使用，应重新读取这些回写产物，而不是继承当前上下文
- `preschedule` 通常是长任务；主代理等待该 subagent 时默认使用较长等待窗口，不因短超时或中间沉默提前回收
- 除非 `preschedule` 已明确返回 `done`、`blocked` 或等价最终状态，否则不得关闭或回收该 subagent
- 除非用户明确指定模型，否则 `preschedule` 默认继承当前会话模型与推理档位，不硬性绑定具体模型名称

## 前置条件

`initial` 已完成。从 store 读取：
- `structure.fubiao_title_idx`（split 用）
- `delivery.*` / `contact.*` / `deadline.*`（填充用，不重复查文档）

## 输出

这一任务至少应产出：

- 完整填充后的前附表文件
- `output.preschedule` 或等价 store 结果
- 重要标记补充表
- 补充投标须知条款表
- 需要人工确认的缺失项或不一致项

产物边界约束：

- `preschedule` 输出文件只包含“投标人须知前附表”标题和前附表主表
- 不把“前附表之附表一/附表二/附表X”并入 `raw docx` 或 `filled docx`
- 各类附表、货物清单、限价表、交货信息表仅作为查值来源使用
- 如需在结果中说明来源，应写“来源：附表一/货物清单附件/招标公告”，而不是把附表正文整体复制进前附表产物

### `preschedule` 完成态

只有同时满足以下条件，`preschedule` 才能标记为完成：

- 已完成七个步骤，而不是只做 `split` 或只读主表
- 引用类字段已尽量回填；无法确定的已显式标注缺失或待确认
- 实质内容的一致性检查已执行，并留下差异记录或“未发现差异”记录
- 全文重要标记扫描已执行
- 补充投标须知已检查；没有补充文件时也要显式写明“无”
- `raw docx`、`filled docx`、summary、task store / 等价结构化结果已回写到当前 workspace

以下状态都不算完成：

- 只拆出“标题 + 主表”
- 只读出表格却未处理引用类字段
- 只回填部分条款就直接给第二阶段使用

## 任务目标

当前的七个步骤已经覆盖主流程，但这里要强调两个核心目标：

1. 把前附表中的字段尽可能填完整，并写清来源
2. 帮投标人快速掌握前附表中的关键约束和容易遗漏的信息

这一任务的难点不在机械填表，而在于字段经常需要反复查表：

- 有些项目把值放在招标文件正文
- 有些项目把值放在招标公告
- 有些项目把值放在附件表格
- 同一个字段在不同项目里的表头、位置和表达方式都不固定

因此不能假设字段位置固定，也不能把表格定位规则写死。

## 查表规则

凡是出现以下情况，都应显式参考 `phase1-preschedule-field-lookup.md`：

- 条款内容写的是“见招标公告”“见附件”“详见附表”
- 需要到表格里查一个具体值
- 表格位置或列名在不同项目里不稳定
- 值可能同时出现在正文、表格和附件中，需要做回退查找

原则是：

- 先读 store 中已经抽出的稳定字段
- 再按 `field-lookup` 的回退链路查 DOCX 表格、DOCX 全文、XLSX 附件
- 不要硬编码表格位置或列名
- 找不到就明确标注缺失，不留空白

## 七个步骤

执行节奏要求：

- 严格按步骤推进，完成一步后再决定下一步读取什么
- 不要在第1步就预读后面所有附件、所有章节和所有工具文档
- 如果某一步未触发，例如没有补充投标须知，也要显式记录“未触发 / 无”

强制中间产物：

- 第2步后必须产出 `preschedule_ledger`
- `preschedule_ledger` 至少逐行记录：
  - `条款号`
  - `条款名`
  - `当前文本`
  - `分类（literal / ref / blank）`
  - `下一步动作`
  - `来源状态`
- 没有 `preschedule_ledger`，不得进入第3步

### 第1步：拆分并解包
`split_by_range(招标文件, start=fubiao_title_idx, end=fubiao_title_idx+2)` → `unpack`

说明：

- 前附表产物默认只保留「标题段落 + 主表格」共 2 个 body 元素
- 如果标题后紧跟的是附表标题、附表说明或附表表格，这些内容不属于 `preschedule` 输出边界
- 如果 split 出来有多于 1 张表，用 `list_tables` 确认主表的 body_idx，并重新收缩范围到“标题 + 主表”
- 附表内容在第3步作为字段来源查询，不在第1步并入拆分结果

### 第2步：读取前附表全部条款
`read_table(unpacked, body_idx=N, key_col=0)` 读整张表。
对每行的「编列内容」分类：
- **引用类**（含「见招标公告」「见附表一」「XX」「待填」）→ 进入第3步
- **实质内容**（有具体值）→ 进入第4步
- **空白** → 标注「【待确认】」

### 第3步：填充引用类字段
按 `phase1-preschedule-field-lookup.md` 定义的四条路径查找。

凡是需要查表、查正文或查附件定位值的字段，也统一参考这份文档，不要单独发明新路径。

**效率优先**：先查 store —— `delivery.*` / `contact.*` / `deadline.*` 在 init 阶段已提取，直接 `store_get` 读取，不重复查文档。

常见字段对应：
- `招标人` → `contact.招标人名称 / 地址`
- `代理机构` → `contact.代理机构名称 / 地址 / 联系人 / 电话`
- `招标范围` → `meta.*`
- `交货期` → `delivery.首批交货日期 / 最后一批交货日期 / 交货方式`
- `交货地点` → `delivery.交货地点`
- `最高投标限价` → 附表一（`list_tables` 找含「最高限价」列的表 → `extract_table_rows`）
- `投标截止时间` → `deadline.投标截止时间`

每次 `replace_text` 写入时在值后标注来源，如：`（来源：货物清单附件）`

这里特别强调：

- “引用附表一取值”不等于“把附表一并入前附表产物”
- 涉及附表一取值的相关条目允许引用附表一结果回填，但附表一正文仍留在原招标文件中，不复制到 `preschedule` 输出
- 引用类字段必须按条款逐项处理；一次只解决一个 unresolved 条款
- 查到值后应立即回写 `preschedule_ledger` / task store，再继续下一项
- 禁止把整张前附表的所有引用字段一次性批量查值

### 第4步：一致性检查
对前附表中有实质内容（非引用）的条款，找正文对应位置比对。

**重点检查**（这些最容易不一致）：

| 检查主题 | 检查内容 | 正文查找方式 |
|---|---|---|
| 投标有效期 | 投标有效期（前附表 vs 通用条款默认值）| `find_by_regex(pattern=r"投标有效期.*\d+日")` |
| 财务年份要求 | 财务年份（如2022-2024 vs 2021-2023）| `find_by_regex(pattern=r"近年财务\|财务.*年份")` |
| 诉讼及仲裁年限 | 诉讼年限（3年 vs 5年）| `find_by_regex(pattern=r"诉讼及仲裁")` |
| 合同签订要求 | 是否重复出现且内容不同 | 统计同主题要求出现次数 |

发现不一致：在对应单元格内追加红色小字注释段落，格式：
`⚠【不一致】正文body[N]：XXX；前附表：XXX。以前附表为准，请人工核查。`

这是 mandatory 步骤；即使未发现不一致，也必须显式记录“未发现差异”。

### 第5步：扫描全文重要标记
扫描范围：全文，排除前附表自身（即“标题 + 主表”的实际输出范围）和第六章格式文件。

收集条件：段落含 `★ ● ☑ □` 特殊字符，**或**段落有非黑色颜色（读 `<w:rPr><w:color>` 属性，值不在 `000000/AUTO` 内）。

过滤：去掉纯表头、纯格式说明（长度<15字），保留对投标人有实质影响的。

以 KV 表格追加到前附表末尾，标注来源 body_idx 和标记类型。

这是 mandatory 步骤；即使无结果，也必须显式写 `none_found` 或空结果表。

### 第6步：补充投标须知（如有 xlsx / docx）
读补充投标须知（通常含「条目名称/内容主题」列，个别文件也会带编号）。
与前附表条款名称对比，找前附表没有覆盖的条款。
以 KV 表格追加，标注「来源：补充投标须知对应条目」。

这是 mandatory 步骤；即使当前项目不存在补充投标须知，也必须显式写明“无补充投标须知 / 未触发”。

### 第7步：重新打包
`pack(unpacked, output/前附表_filled.docx, original=fubiao_raw.docx)`
正常的段落数变化：+15 ~ +60（视补充内容多少）。
写入：`store_set(sp, "output.前附表", output_path)`

打包前完成门槛：

- 全部条款都已经进入以下状态之一：
  - `literal_checked`
  - `resolved`
  - `pending_human`
  - `pending_asset`
- 不存在 `unclassified` 条款
- 第4/5/6 步均已执行并留下结果
- 仅完成 `split`、`read_table` 或抽表摘要，不构成前附表完成

### 步进回写

- 每完成一步，都应尽量把中间状态写回当前 workspace 的 task store 或 summary
- 后续如需换 subagent 继续处理，应以这些回写产物作为唯一继续依据
- 不要把“前面几步已经在脑子里做过”当作继续执行的前提

## 注意事项

- 遇到跨多个 `<w:t>` 的段落（`read_node_xml` 诊断）：精确匹配单个 run 内容
- 一致性注释追加在单元格内，不替换原始内容
- 对无法确定的内容写 `【⚠数据缺失】已查 DOCX/全文/附件，请人工确认`，不留空白
- 本流程只产出前附表及其辅助清单，不生成任何商务文件内容；与 `phase2` 相关的模板、章节树、签字盖章编排均禁止在此阶段读取
