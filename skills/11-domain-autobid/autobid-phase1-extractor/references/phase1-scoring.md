# 评分办法提取

## 前置条件

`initial` 已完成。从 store 读取：
- `structure.ch3_start / ch3_end`
- `meta.分标名称 / 分标编号`

## 输入与读取边界

这一流程优先读取当前活跃 workspace `input/files/` 下的招标文件、招标公告、相关附件，以及 `initial` 已写入的 `files.*` 和章节边界。

评分办法提取的主来源应是当前项目文件本身，不应先从 `Data/` 中寻找现成答案。

## 任务隔离、等待与模型

- `scoring` 默认由独立 subagent / 独立上下文执行，不与 `preschedule` 或 `qualifications` 混做
- 开工时先只看当前文档和所列 `base-tools`，不预读 `phase2` 文档
- `scoring` 通常是长任务；主代理等待该 subagent 时默认使用较长等待窗口，不因短超时或中间沉默提前回收
- 除非该任务已明确返回 `done`、`blocked` 或等价最终状态，否则不得关闭或回收该 subagent
- 除非用户明确指定模型，否则 `scoring` 默认继承当前会话模型与推理档位，不硬性绑定具体模型名称

## 最终交付要求

这一子流程的**最终交付应以独立 `docx` 为主**，而不是只留下参数摘要。

交付原则：

- 直接把第三章中与当前分标、包号有关的评分内容从招标文件原文拆成独立 `docx`
- 保留原有标题、表格、编号、段落结构和版式，不要把评分表改写成纯文本后再导出
- 如果某一交付件来自多个不连续范围，应按原始顺序拼成一个独立 `docx`
- `scoring.*`、json、markdown、store 结果只是结构化辅助产物，不能替代 `docx` 交付件

建议至少交付，都为独立文档：

- `output.报价评分标准.docx`
  - 该文档除保留原始“报价评分标准”原文外，还应**合并当前分标对应的分值构成及参数摘要**
  - 参数摘要的来源仍然是“分值构成及参数”表，但**不再单独输出一个参数 docx**
- `output.商务评审细则.docx`
- `output.技术评审细则.docx`

## 工具 Skills 路由

执行本流程时，应明确查看 `../../autobid-office-tools/references/` 中对应文档，再调用工具，不要只凭业务理解直接操作。

最少应查看这些文档：

- `../../autobid-office-tools/references/docx-inspect.md`
  用于定位第三章里的标题、表格和 `body_idx` 范围
- `../../autobid-office-tools/references/docx-table.md`
  用于读取分值构成参数表、评分细则表，以及在拆出独立评分 `docx` 后处理宽表版式问题
- `../../autobid-office-tools/references/docx-split.md`
  用于 `split_by_range` 拆出独立评分 `docx`，或在需要时用 `join_by_manifest` 拼接多个范围
- `../../autobid-office-tools/references/task-store.md`
  用于把参数、适用范围和交付 `docx` 路径写回 store

一句话规则：

- 先 `inspect / list_tables`
- 再判定适用范围
- 再 `split_by_range / join_by_manifest`
- 最后把 `docx` 路径和结构化参数一起写回 store

## 四个步骤

### 第0步：先看工具文档

先阅读并遵循：

- `../../autobid-office-tools/references/docx-inspect.md`
- `../../autobid-office-tools/references/docx-table.md`
- `../../autobid-office-tools/references/docx-split.md`
- `../../autobid-office-tools/references/task-store.md`

这一阶段的核心不是“解释评分规则”，而是“把对应原文范围准确拆成独立 docx，并补齐结构化参数”。

评分提取高度依赖表格，只要涉及参数表、商务细则表、技术细则表，就必须回到 `../../autobid-office-tools/references/docx-table.md` 查看规范，不要跳过表格工具流程直接凭肉眼判断。

### 第1步：读取第三章结构
`inspect(招标文件, body_range=(ch3_start, ch3_end), include_elements=True)`

从返回的 `body_elements` 里找：
- 类型=`tbl` 且含「分标名称/报价评分标准/权重」列 → 分值构成及参数表
- 类型=`p` 且文字含「报价评分标准及分值构成」→ 报价说明段落起点
- 类型=`p` 且文字含「商务评审细则 / 商务评审标准 / 商务通用标准 / 商务专项标准」→ 商务评分范围候选标题（记录全部）
- 类型=`p` 且文字含「技术评审细则 / 技术通用标准 / 技术专项标准」→ 技术评分范围候选标题（记录全部）

### 第2步：提取分值构成参数
分值构成表通常是**双行表头**（第一行大列名，第二行子列名如技术/商务/价格/C值/n1/n2）。
`extract_table_rows` 只返回第一行表头，子列需直接读 XML 的第2行。

这一段必须先阅读 `../../autobid-office-tools/references/docx-table.md` 再执行。标准顺序：

1. `list_tables` 确认目标表 `body_idx` 和实际表头
2. 如果需要整表理解，先 `read_table`
3. 如果需要按分标名称精准取行，再 `extract_table_rows(match={分标名称列: 分标名称})`
4. 双行表头或合并单元格导致 `extract_table_rows` 信息不足时，再回到底层 XML 读取第二行子列

不要：

- 不看 `headers_indexed` 就假设列序号
- 直接把第一行表头当完整语义
- 在业务文档里重新发明一套表格读取规则

写入 store：`scoring.报价评分标准 / 技术权重% / 商务权重% / 价格权重% / C值 / n1 / n2 / W1 / W2`

同时要求：

- 把当前分标对应的参数摘要合并进 `output.报价评分标准.docx`
- 不再单独交付 `output.分值构成及参数.docx`

### 第3步：确定适用的商务和技术评审细则
不要把第三章的评分标准结构写死。尤其是商务部分，当前项目里可能出现：

- 只有一个 `商务评审细则`
- 先给一个 `商务通用标准`，再给一个或多个 `商务专项标准`
- 不写“细则”，而是直接写“商务评审标准”“商务部分评分标准”等近义标题
- 标题括号或邻近段落中列出多个分标名称/品类范围

技术评审细则通常按品类范围划分，**括号内列出了多个分标号**，需判断本标包是否在其中。

```
# 示例标题：「技术评审细则（014套管监测系统、019图像在线监测装置、027变电站在线智能巡视系统）」
# 判断方式：分标名称的关键词（如"变电站在线智能巡视"）in 标题全文
```

操作：
1. 从第1步得到全部商务/技术评分标题候选列表，不要先验假设商务只有一个
2. `read_body_xml` 读每个标题段落全文，必要时连同相邻说明段一起看
3. 用当前招标项目上下文判断适用范围：
   - 当前分标名称、分标编号、包号
   - 分标名称关键词或品类关键词
   - 标题中的括号范围、邻近说明文字、表头中的“适用标包/适用分标”
4. 商务部分判断规则：
   - 若标题或邻近说明明确写 `适用于所有标包 / 通用标准 / 通用商务`，标记为通用候选
   - 若标题或邻近说明明确命中当前分标名称、品类范围、包范围，标记为专项候选
   - 若同时存在通用和专项，且专项明确约束当前分标，不要简单覆盖；要判断是“专项替代通用”还是“专项补充通用”
   - 无法确定时，优先保留更多上下文，并在结果中标记 `pending_human`
5. 技术部分判断规则：
   - 用 `分标名称关键词 in 标题文字` 判断（不要用精确匹配，分标名称可能缩写）
   - 找到匹配标题后，取「该标题 body_idx」到「下一个同层标题或章节 body_idx」

如果候选范围里是表格，不要只截标题段。应结合 `../../autobid-office-tools/references/docx-table.md` 先确认标题后的目标表 `body_idx`，再决定拆分范围。

### 第4步：拆分输出
用第1步识别的各段范围 `split_by_range` 输出独立 docx。

如果某一评分交付件实际来自多个不连续范围，不要退化成 markdown 摘要，应按 `../../autobid-office-tools/references/docx-split.md` 使用 `join_by_manifest` 拼接成一个独立 `docx`，继续保持原格式。

标准输出：
- `第三章_报价评分标准.docx`
  - 包含原始报价评分标准说明
  - 还包含从参数表中提取的当前分标参数摘要（如报价算法、技术/商务/价格权重、C值、n1、n2、W1、W2）
- 商务部分：
  - 若只有一个适用范围：`第三章_商务评审细则.docx`
  - 若存在通用+专项：`第三章_商务评审细则_通用.docx` 和 `第三章_商务评审细则_{分标名称}.docx`
- 技术部分：
  - `第三章_技术评审细则_{分标名称}.docx`
  - 若未命中专项，则输出 `第三章_技术评审细则_通用.docx`

写入 store：
- `output.报价评分标准`
- `output.商务评审细则` 或 `output.商务评审细则.通用 / output.商务评审细则.专项`
- `output.技术评审细则`
- `scoring.商务标准类型`（如 `通用` / `专项` / `通用+专项` / `pending_human`）
- `scoring.*` 中保留从参数表提取出的结构化参数

要求：

- 这些 `output.*` 应直接指向最终交付的独立 `docx`
- 不要只在 json 里写参数；参数虽不单独输出 docx，但必须合并进 `报价评分标准.docx`
- 如果拆出的评分 `docx` 包含宽表、表格超页、列宽比例失衡，应返回 `../../autobid-office-tools/references/docx-table.md` 查看 `fit_table_to_page` 的规范和经验，不要在业务文档里临时决定缩放策略

## 注意事项

- 技术评审细则标题括号内分标号是范围，不是精确一一对应，用「关键词包含」判断
- 商务评分部分也可能写成「商务通用标准」「商务专项标准」「商务评审标准」，不要硬编码标题名
- 商务部分不要预设“只会有一个表”；要结合当前分标上下文判断到底取通用、专项，还是两者都保留
- 如果商务通用标准是底座、专项标准是补充，则两部分都应输出，不能只留其中之一
- 如果全章没有找到适用于本标包的技术评审细则，说明该分标使用通用标准，输出通用技术评审细则表（通常在所有专项细则之前）
- 第二阶段如果要复核评分依据，应优先打开这里产出的独立 `docx`，而不是回到整章重新找范围
- 只要评分内容落在表格里，就继续以 `../../autobid-office-tools/references/docx-table.md` 为表格操作规范来源；本业务文档只定义“取哪张表、为什么取”，不定义“表格工具怎么用”
