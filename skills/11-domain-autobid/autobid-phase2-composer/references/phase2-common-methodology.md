# 第二阶段通用方法论

适用范围：

- `商务文件`
- `技术文件`

执行具体业务文档前，先遵循：

- `../SKILL.md`
- `phase2-mode-reference.md`（只做模式路由，具体模式按需读取 `modes/*.md`）

## 通用任务目标

这一层只处理两类共性问题：

- 如何把招标文件原始结构整理成可执行的 `输出章节模板`
- 如何在不丢语义的前提下完成内容填写、格式统一、资料挂载和最终组装

## 通用输入

通用方法论默认依赖：

- 招标文件中的 `投标文件组成目录`
- 招标文件中的 `投标文件格式`
- 招标文件正文中的提交条件、模板提示、章节说明
- 第一阶段沉淀的结构化结果
- 当前工作区格式规范
- 当前工作区与 `Data/` 中的可复用模块、企业资料和项目素材

## 上下文卫生与任务包

### 最小读取序列

- subagent 默认只读取 4 类内容：
  - 主代理下发的任务包
  - 当前章节相关的上游结构化结果
  - 当前章节必需的业务文档
  - 当前章节必需的 `base-tools`
- 未触发缺证据条件时，不回读整份招标文件，不预读不相关章节
- 商务章节若依赖前附表字段，先读 `preschedule` 的回写结果；只有摘要不足时，才允许定点回读招标文件对应页段

### 主动遗忘

- 每完成一个 `group_node` 或稳定章节组，都应把当前上下文压缩为：
  - `章节摘要`
  - `来源`
  - `未决项`
- 上述结果必须回写 task store、章节树或等价元数据
- 后续子任务默认只读取这些摘要，不继承上一章全文上下文

### 强制主从调度

- 第二阶段强制使用 subagent 主从调度；不能创建或等待 subagent 时，返回 `blocked_by_subagent_unavailable`
- 主代理只负责拆分、依赖检查、上下文清理、长期等待和结果合并；subagent 只负责局部求解
- 一个代理一次只处理一个清晰角色下的一个稳定范围
- 如果当前范围仍跨多个稳定章节、多个章节组或多个处理模式，当前代理的责任是继续拆分，而不是直接做完
- 不得让同一个 subagent 同时负责：
  - 前附表补齐
  - 商务正文编排
  - 大量资料挂载
  这类跨语义混合任务

### 依赖章节挂起

- 如果当前章节依赖 `preschedule` 或其他上游结果，而上游未完成，应显式回写：
  - `blocked_by_preschedule`
  - 或等价的挂起状态
- 不得静默跳过，也不得自行猜填

### 递归委派规则

- 第二阶段默认采用 4 类角色：
  - `主代理`
    只负责全局目录冻结、依赖门禁、任务包编排、质量门禁和最终组装
  - `文件级 manager`
    只负责单个文件的本地章节树、章节分发、局部验收和回写
  - `章节组 manager`
    当接到 `group_node` 或多个稳定 sibling 时，继续拆成更小的 child worker，并负责该组最终组装
  - `叶子 worker`
    只负责一个不可再拆的稳定章节，或一个极小机械动作
- 判断规则：
  - 如果当前范围仍包含多个稳定章节、多个模式或多组来源材料，当前代理不是叶子 worker，必须继续拆分
  - 只有范围已经缩到单章，或继续拆分的成本明显高于执行成本时，当前代理才允许直接落地
- 任何上层代理都不得因为“自己已经有上下文”而直接串行完成下层全部任务
- 每一层代理都只保留自己需要的最小上下文，并通过任务包把必要信息传给下一层

### 等待、回收、状态回报与模型规则

- 第二阶段的章节制作、资料挂载、DOCX 组装和校验通常都是长任务；主代理默认按“分钟级等待”而不是“秒级轮询”管理 subagent
- 对关键路径 worker，如果一次等待未返回最终状态，必须继续等待或让其后台继续运行；不得因为短超时、暂时无输出或中间沉默就提前回收
- 只有当 subagent 已明确返回 `done`、`blocked`、失败结论，或任务已被上层重新切换范围时，才允许关闭或回收
- 非关键路径 worker 也不要高频 busy-poll；应尽量减少无意义短轮询，把主代理时间留给其他非重叠工作
- subagent 必须定期回报状态：开工后、每个可验证小步骤后、进入长工具操作前、长任务每 10-15 分钟或每个工具调用结束后、阻塞时、结束时
- 状态回报必须包含当前阶段、负责范围、已读取 md、已回写产物、未决项、下一步和验证
- 默认不在规则中绑定具体模型名称；subagent 应继承当前会话模型与推理档位；下发时不要显式指定模型
- 只有两种情况允许显式覆盖模型：
  - 用户明确指定
  - 平台能力边界或任务类型存在清晰、必要且可说明的理由

## 通用执行流程

1. 识别目标范围，定位商务文件或技术文件的正文区间
2. 生成 `源章节清单`
3. 生成 `输出章节模板`
4. 冻结章节目录、标题角色和重编号规则
5. 先分派文件级 manager，再递归分派章节组 manager / 叶子 worker
6. 为每个输出节点选择处理模式
7. 显式读取格式规范后逐章处理
8. 汇总章节并输出最终 `.docx`

补充要求：

- 在第5步分派前，主代理先完成依赖检查
- 文件级 manager 在继续分派前，先完成自己负责文件范围内的局部目录确认
- 在第7步逐章处理时，每章都应有明确的 `done` 条件，至少覆盖：
  - 模板确认
  - 字段填写
  - 资料挂载
  - 格式检查
  - 元数据回写
- 未满足 `done` 条件，不得标记当前章节组完成

## 通用方法论

### 1. 先建输出模板，再写内容

先区分两份结构：

- `源章节清单`
  忠实记录招标文件原始层级、原始标题和提示文字
- `输出章节模板`
  只保留本次最终提交需要的结构，并确定最终编号和父子关系

后续所有填写、重编号、模板抽取和组装，都以 `输出章节模板` 为准。

### 2. 目录确认后再分派章节任务

第二阶段默认不是“读到一章就直接开写”，而是先由主代理完成章节目录确认。

主代理至少要先确认：

- 哪些章节保留、删除、留空
- 最终章节编号、父子关系和重编号规则
- 每章的正式标题、提示标题、开头说明、附注文字分别属于什么角色
- 哪些章节适合独立分发，哪些章节必须按 `group_node` 成组处理

分派规则：

- 只有在 `输出章节模板` 已冻结后，才把章节分给 subagent
- 主代理只分派文件级 manager，不直接把整份文件内容自己做完
- 文件级 manager 如果收到的范围仍是多个稳定章节组，必须继续拆给章节组 manager / 叶子 worker
- `group_node` 默认由章节组 manager 持有；它要继续下发 child worker，而不是自己串行完成整组内容
- 优先按“完整章节 / 稳定章节组”分派，不按零散页段切开
- 每个 subagent 开工前都要先读：
  - `phase2-common-methodology.md`
  - 自己负责的 `phase2-business-file.md` 或 `phase2-tech-file.md`
  - `phase2-mode-reference.md`（先选模式；选中后只读一个 `modes/*.md`）
  - 当前章节需要的 `../../autobid-office-tools/references/*.md`
- subagent 只处理自己负责的章节，不自行改动其他章节的全局目录决策
- 如果 subagent 发现目录、标题或编号判断有误，应先回写主章节树和 task store，再继续执行

### 3. AI 负责语义判断，工具负责机械执行

`AI` 负责判断：

- 哪些章节保留
- 哪些章节删除
- 哪些父节点要保留
- 哪些章节需要重编号
- 哪些标题只是模板提示，不应进入最终文件

工具和脚本负责：

- 抽模板
- 替换占位符
- 套版式
- 插图、贴图
- 文档拼接

脚本只能执行已经确定的结构决策，不能代替语义判断。

### 4. 缺资料不硬编，但默认按满足口径组织结论

遇到资料缺失时：

- 先区分“结论性判断”和“硬事实材料”
- 对“是否满足招标文件要求 / 是否符合资格条件 / 是否存在相关情形”这类结论，如果用户未另行推翻且未发现反证，默认直接写 `满足`、`符合`、`无相关情形`
- 这类结论默认不再留 `pending_human`、`用户填写` 或 `【待补】`
- 对签字、签章、日期、个人敏感信息、证照编号、参数值、检测数据、截图和缺失附件，仍不得伪造
- 如招标文件要求必须附真实材料且资料库暂无，只能保留挂载壳子或待补位置，但要优先减少不必要的人为填写槽位

### 5. 用户确认要立刻回写

用户一旦确认某个章节保留、删除、改名、重编号或留空，必须同步回写：

- 对应文件自己的 `章节树`
- 对应文件自己的 `关键约束与经验`
- 对应文件自己的 `task store`

### 6. 模板先校验，再决定复用方式

跨项目反复出现的同语义章节，默认先判断：

- 是否已有稳定模板或模块
- 是否只是项目字段、日期、章节号需要替换
- 是否只需按产品类别切换模板
- 模板标题、模板开头、正文文本、表格内容分别是否符合当前招标文件要求
- 模板主体是否本来就是图片/扫描件拼接出来的 `DOCX`

只有当现有模板无法覆盖当前语义时，才退回到从零生成。

模板复用时至少显式检查四件事：

- `模板标题`
  是否要保留正式标题、删除 `XX格式 / XX模板 / 示例`
- `模板开头`
  开头说明、编制说明、适用范围、提醒文字是否属于本章正式内容
- `图片主体`
  如果大部分内容是图片/扫描件拼接出来的 `DOCX`，优先直接拼接复用，不重做图片区
- `文本 / 表格`
  图片之外的文本和表格必须对照招标文件格式规范检查，并把该填写的内容填写完整

模板来自招标文件、`Data/modules/` 或历史项目，都不能因为“看起来像现成模板”就直接整章照搬。

### 7. 一张输出表可以来自多个源表

第二阶段填写表格时：

- 以最终输出表结构为准，不要求和单个源表一一对应
- 允许从多个章节、多个源表抽取字段后，合并填入同一张输出表
- 涉及技术规范书回填的表格，先读编制说明和字段语义，不把“找到同名表”当作完成
- 需要保留的必填行、保底行，即使暂无数据也不得删行，只能留空
- 合并来源应在元数据中记录，避免后续追溯失真

### 8. 表格和贴图可以分开做，再统一组装

同一章如果同时包含：

- 结构化信息表
- 图片、扫描件、截图或贴图证明

可先分别产出：

- `信息表 partial`
- `贴图/附件 partial`

最后再按 `group_assembled` 规则统一编入大章节，避免在单次写入里同时处理过多版式和关系文件。

### 9. 先保证成稿可读性，再保证字段不丢

对项目名称、单位名称、地址、设备名称等长字段：

- 可以按语义做智能分行
- 不把多个长字段硬塞在同一单元格或同一行
- 不因为追求紧凑而破坏渲染效果

可读性优化不能改变原字段含义，也不能擅自删减字段。

### 10. AI 写作必须受规范书和知识库约束

对技术服务、培训、制造工艺、保障措施等需要 AI 组织文字的章节：

- 先读招标要求和技术规范书
- 再读企业模板、知识库或历史成熟模块
- 最后才做项目级改写

这类章节允许生成，但不允许脱离依据自由扩写。

## 通用处理模式

第二阶段的模式细节按资源拆分，默认流程是：

1. 先读 `phase2-mode-reference.md` 判断模式。
2. 选中模式后，只读取一个对应的 `modes/*.md`。
3. 不要为了一个章节一次加载全部模式文件。

模式索引：

- `table_fill` -> `modes/table-fill.md`
- `template_fill` -> `modes/template-fill.md`
- `fixed_shell_image` -> `modes/fixed-shell-image.md`
- `module_docx` -> `modes/module-docx.md`
- `rule_generated` -> `modes/rule-generated.md`
- `group_assembled` -> `modes/group-assembled.md`
- `conditional_ignore` -> `modes/conditional-ignore.md`

选择模式时，优先看“章节语义”，不要只看文件名或标题字面。

## 格式规范

### 读取顺序

格式规范默认按以下优先级读取：

1. `meta/phase2_business_format_spec.json` 或 `meta/phase2_tech_format_spec.json`
2. `meta/phase2_format_spec.json`
3. `input/standards/phase2_format_spec.json`
4. 招标文件 `投标文件格式` 中的明确要求

如果以上几层都没有写清，先补齐格式规范，再开始逐章制作。

### 使用原则

- 每个章节开始前，都要显式读取格式规范
- 标题、正文、表格、图片、页眉页脚、页码按同一套规范统一
- 模块模板、招标文件原模板、资料库模板都不能直接信任原始版式
- 即使直接套 `module_docx`，也仍然要统一当前项目的页边距、字体、logo、页眉页脚和表格样式

### 图片与分页经验

- 标题、短说明后如果紧跟图片，标题段应设置为“与下段同页”
- 当前页放不下时，优先让“标题 + 第一张图”一起移到下一页
- 如必须缩放，优先只轻度缩小第一张图，避免整组图片全部失真
- 对敏感扫描件，只处理外层壳和版式，不主动分析图片内容

## 工具与组装经验

### 模板复用

- 可以从招标文件切片抽模板
- 也可以直接复用 `Data/modules/` 下的模块模板
- 模板不能因为来自招标文件或 `Data/modules/` 就直接整体照搬
- 复用前至少检查 `模板标题`、`模板开头`、`图片主体`、`文本 / 表格` 四类内容
- 如果模板只覆盖子章节，优先产出 `child_partial`
- 如果模板已经是完整大章节，可直接作为 `group_final`
- 对同语义但分产品类别的模板，先选对类别，再做项目字段替换
- 大部分由图片或扫描件拼接出的 `DOCX`，优先直接复用图片和关系文件；不要把图片区改写成低保真重排版
- 只有图片之外的文本、表格、项目字段和说明文字，才需要按当前招标文件格式逐项检查和填写

### 组装规则

- 同一 `group_node` 下的子章节，最终应由大章节文件统一组装
- 同组被删除的节点不进入最终编号，保留节点按顺序连续重排
- 带图片或扫描件的章节，不能只拼 body，必须做关系级合并
- 同一章若拆成 `信息表 partial` 和 `贴图 partial`，最终也按同组规则合并

### 工具边界

- 不自动决定章节是否保留
- 不自动决定父节点是否折叠
- 不自动伪造缺失资料
- 不把模块文件名当作唯一真相

## 必须回写的元数据

每完成一个章节或一个大组，至少回写：

- 源节点标题
- 输出节点标题
- `body range`
- 保留 / 删除原因
- 是否重编号及原因
- 处理模式
- 主要依赖来源
- 未决项和待补资料

## 通用注意事项

- 模板提示类标题，如 `XX格式`、`XX模板`、`示例`，通常不进入最终文件
- 父节点如果包含上传路径、提交条件、适用范围或操作说明，不能简单折叠
- 章节是否起新页、是否独立分页，应看最终交付可读性，不机械沿用原文
- 留空项要符合招标文件和用户要求，尤其是签字、盖章、日期和个人敏感信息
- 对“符合性 / 满足性 / 情况说明”类结论，默认按用户确认口径直接成文，不额外制造 `用户填写` 槽位
- 对输出表来自多个源表的场景，要保留“输出模板优先”的意识，不机械照搬某一个源表版式
- 对需要 AI 写作的方案、服务、保障类章节，优先使用“规范书约束 + 知识库约束 + 模板复用”的组合，而不是从空白页自由发挥


- `偏差表`

默认做法：

- 从招标文件抽原始模板
- 删除 `（格式）` 提示
- 读取格式规范并显式覆盖 section/layout
- 直接在原表中填值
- 默认填写一行，序号1,其余列填 “/” 表示无偏差
- 保留模板空行，不做结构裁剪

## 一句话规则

第二阶段通用方法论的核心是：先用语义判断冻结 `输出章节模板` 和章节目录，再由主代理下发文件级 manager、文件级 manager 继续下发章节 worker，最后把所有确定结论回写到各自文件的元数据中。
