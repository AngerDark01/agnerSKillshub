# 商务文件执行

执行前先遵循：

- `../SKILL.md`
- `phase2-common-methodology.md`
- `phase2-mode-reference.md`（只做模式路由；具体模式按需读取 `modes/*.md`）

开工前屏障：

- 商务文件默认在 `preschedule` 已达到完成态后再启动
- 如果前附表字段仍缺失、冲突或只完成了部分步骤，应先回退补齐 `preschedule`，不要直接继续写商务文件

## 任务目标

商务文件的目标不是写技术方案，而是围绕“是否合规、是否满足资格、是否具备授权、是否有商务得分支撑”来组织材料并完成成稿。

这一子任务至少要完成：

- 明确商务文件最终提交的章节结构
- 形成商务文件自己的 `输出章节模板`
- 完成资格、承诺、授权、偏差表、评分支撑和补充文件的编制
- 输出可直接提交的 `商务文件.docx`

## 商务文件的默认委派拓扑

- 商务文件 subagent 默认是 `文件级 manager`，不是整份文件的执行 worker
- 它的职责默认只有：
  - 维护商务文件自己的 `输出章节模板`
  - 把商务文件拆成稳定章节组
  - 为每个章节组准备任务包并下发
  - 汇总章节产物、回写章节树和 task store
- 如果收到的范围仍包含多个稳定章节组，当前代理必须继续拆分，而不是自己串行做完整份商务文件
- 如果某个章节组仍是 `group_node`，例如 `投标保证金组`、`补充文件组`、`资格证明文件组`、`商务评分支撑组`，当前代理继续拆给 child worker；自己只保留顺序控制和最终组装责任
- 只有当收到的范围已经是叶子章节，或仅剩极小机械动作时，当前代理才可直接执行正文、模板处理或格式统一

商务文件的默认拆分视角可先参考：

- `商务偏差表 / 基础信息表`
- `承诺函 / 授权书`
- `资格证明文件组`
- `财务状况`
- `商务评分支撑组`
- `补充文件 / 扫描件组`

## 输入

商务文件依赖的前置主要是：

- `../SKILL.md`
- `phase2-common-methodology.md`
- 第一阶段的 `preschedule.*`、`qualifications.*`、`scoring.*`、`meta.*`
- 招标文件中的 `商务文件格式`、资格要求、商务评分标准、提交条件和说明文字
- 当前工作区 `input/standards/`、`input/assets/`
- `Data/modules/` 与 `Data/material/` 中可复用的商务模板、证照、扫描件和固定材料

依赖读取顺序默认是：

1. `preschedule.*`
2. `qualifications.* / scoring.*`
3. 招标文件中与当前章节直接相关的正文
4. `Data/modules/` 与 `Data/material/`

## 最终交付物

对外交付物：

- `商务文件.docx`

对内回写产物：

## 商务文件的业务特点

商务文件默认更强调：

- 资格符合性
- 主体信息和承诺响应
- 授权和签章逻辑
- 商务偏差应答
- 商务评分点支撑材料

因此，商务文件的核心不是长篇叙述，而是“结论清晰、证据对应、模板合规、资料挂准”。

## 商务文件章节填写规范

### 1. 资格符合性章节

这类章节通常对应：

- `符合招标文件投标人资格要求的证明文件`
- 招标公告或前附表中引用的资格证明材料

默认做法：

- 先读第一阶段提取出的资格要求
- 再按当前项目的商务文件模板建立“正文应答区 + 补充材料区”或等价结构
- 每条资格要求只先判断“采用哪种处理类型”，不要一开始就做复杂字段建模
- 对“是否满足资格要求 / 是否存在相关情形 / 是否已按要求提供材料”这类判断，若用户未另行否定且未发现反证，默认按 `满足`、`符合`、`不存在相关情形` 正向应答

常用处理类型：

- `承诺型`
  只写明确应答或承诺
- `固定模板型`
  直接套模板
- `固定贴图型`
  优先挂扫描件或固定资料
- `用户填写型`
  仅在必须保留用户亲填内容、签章敏感项或明确缺少不可替代硬事实时使用，不作为资格/情况判断的默认模式
- `时效查询壳子型`
  只保留标题、说明和截图槽位

其中：

- `主应答区` 更适合放承诺、固定模板和固定贴图
- `补充材料区` 更适合放查询截图、时效证明和说明壳子；对纯符合性判断不默认留用户后补槽位

### 2. 基础信息、承诺和授权章节

这类章节通常包括：

- 投标人基本情况表
- 承诺函
- 授权委托书
- 公章或投标专用章授权书

默认做法：

- 优先使用招标文件原模板或已验证的模块模板
- 自动填写项目级公开字段
- 默认保留个人敏感字段、签字、签章、日期为空
- 不擅自补身份证件、个人职务、签名图片等信息

适合自动填的字段通常包括：

- 投标人名称
- 项目名称
- 招标编号
- 分标编号 / 分标名称
- 包号 / 包名称

### 3. 表格响应类章节

这类章节通常包括：

- 商务偏差表
- 基础信息总表
- 需要保留原表结构的商务应答表

默认做法：

- 优先保留原表结构
- 先删 `格式`、`模板`、`示例` 这类提示标题
- 再按格式规范统一表格字号、边框、行距和页面宽度
- 不因为方便填写而随意裁剪模板表格结构

### 4. 商务评分支撑章节

这类章节通常对应：

- 招标文件中的 `商务评分标准` 条款
- 商务评分支撑材料章节

默认做法：

- 先读取第一阶段产出的商务评分细则
- 将适用于当前标包的评分标准放在本章开头
- 评分总表建议新增一列 `对应内容`
- 再按 `项目 -> 评审要素` 动态展开子章节
- 每个 `评审要素` 至少同时考虑：
  - 文字应答
  - 材料挂载

这里的关键不是“把资料堆进去”，而是让评委快速看到：

- 这个点为什么满足
- 这个点为什么可能得分
- 证据材料挂在什么位置

### 5. 扫描件、补充文件和组装类章节

这类章节通常包括：

- 营业执照
- 银行基本账户证明
- 税务登记证明
- 投标保证金组
- 补充文件组

默认做法：

- 优先复用 `Data/modules/` 中的成熟模板
- 资料是扫描件时，只处理壳子、标题和版式，不主动分析图片内容
- 同组章节先分别产出子章节，再由大章节统一组装
- 带图片的章节最终合并时，必须做关系级拼接，不只拼正文

## 商务文件的常用模式映射

可优先按以下语义选模式：

- `商务偏差表` -> `table_fill`
- `承诺函 / 授权书` -> `template_fill`
- `证照扫描件 / 证明扫描件` -> `fixed_shell_image`
- `基础信息总表 / 已成形整章模板` -> `module_docx`
- `投标保证金组 / 补充文件组` -> `group_assembled`
- `明确不适用的章节` -> `conditional_ignore`

补充规则：

- `group_assembled` 只定义章节处理方式，不授权当前代理吞掉整组任务
- 如果当前代理拿到的是 `投标保证金组`、`补充文件组`、`资格证明文件组` 等大章节，它默认仍然是组装 manager，需要继续把子章节分给 child worker
- 只有已经缩到单个稳定子章节时，当前代理才直接执行对应模式

各模式的标准动作和特殊说明不要在商务文件入口一次性加载。先读 `phase2-mode-reference.md` 选模式，再只读对应文件：

- `table_fill` -> `modes/table-fill.md`
- `template_fill` -> `modes/template-fill.md`
- `fixed_shell_image` -> `modes/fixed-shell-image.md`
- `module_docx` -> `modes/module-docx.md`
- `group_assembled` -> `modes/group-assembled.md`
- `conditional_ignore` -> `modes/conditional-ignore.md`

## 商务文件特有注意事项

- 商务文件里的很多章节本质是“提交合规性证明”，不是“自由发挥型写作”
- 只要能用清晰表格、明确承诺或现成证据解决的问题，就不要扩写成大段空话
- 评分支撑章节要围绕评分点逐项响应，不要脱离评分标准单独展开
- 涉及签字、盖章、个人身份信息时，默认从严留空
- 同一类证明材料不要在多个章节重复挂载，除非招标文件明确要求重复提交
- 对“满足要求 / 符合条件 / 无相关情形”这类商务判断，默认直接写成提交口径，不额外要求用户补判断性文字

## 必须回写的商务元数据

至少回写：

- 商务文件源章节结构
- 商务文件输出章节模板
- 每章采用的处理模式
- 主要引用来源和所挂材料
- 需人工确认的未决项
- 因用户要求而保留空位的字段

## 一句话规则

商务文件的核心是：围绕资格、承诺、授权、偏差和商务评分支撑，把每个章节做成“结构正确、应答清楚、证据可挂、格式合规”的提交文件，并由文件级 manager 继续拆分到章节 worker，而不是让上层代理整份串行施工。
