# 技术文件执行

执行前先遵循：

- `../SKILL.md`
- `phase2-common-methodology.md`
- `phase2-mode-reference.md`（只做模式路由；具体模式按需读取 `modes/*.md`）

## 任务目标

技术文件的目标不是简单复制模板，而是围绕“是否满足技术要求、是否具备实施能力、是否能支撑技术得分”来组织输出结构和正文内容。

这一子任务至少要完成：

- 明确技术文件最终提交的章节目录、编号层级、标题角色和章节边界
- 明确技术文件最终提交的章节结构
- 形成技术文件自己的 `输出章节模板`
- 完成参数响应、方案说明、实施组织、服务承诺、技术资料和技术评分支撑
- 输出可直接提交的 `技术文件.docx`

## 输入

技术文件依赖的前置主要是：

- `../SKILL.md`
- `phase2-common-methodology.md`
- 第一阶段的 `scoring.*`、`meta.*` 以及与技术条款相关的结构化结果
- 招标文件中的 `投标文件组成目录`
- 招标文件中的 `技术文件格式`、技术规范书、技术要求、技术评分标准和提交条件
- 当前工作区 `input/standards/`、`input/assets/`
- `Data/modules/` 与 `Data/material/` 中可复用的技术模板、说明书、图纸、案例、检测报告、认证资料等

## 最终交付物

对外交付物：

- `技术文件.docx`

对内回写产物：

- `meta/phase2_tech_章节树.md`
- `meta/phase2_tech_关键约束与经验.md`
- `meta/.task_store_phase2_tech*.json`

## 技术文件的业务特点

技术文件默认更强调：

- 技术参数符合性
- 方案能力与实现路径
- 供货、实施、组织和进度安排
- 服务、培训、售后和保障能力
- 技术评分点支撑材料

因此，技术文件的核心不是堆形容词，而是“条款有响应、方案有结构、结论有证据、评分点有支撑”。

## 技术文件的执行组织

- 技术文件 subagent 默认是 `文件级 manager`，先确认 `投标文件组成目录`、`技术文件格式`、章节边界和 `输出章节模板`，再开始分发
- 文件级 manager 默认只负责章节树、任务包、局部验收和回写，不直接串行完成整份技术文件
- 技术文件默认按“完整章节 / 稳定章节组”分派给 subagent，不按零散页段拆任务
- 如果文件级 manager 收到的范围仍包含多个稳定章节组，它必须继续拆给章节组 manager / 叶子 worker
- 如果某个章节组本身还是 `group_node`，当前 manager 继续拆给 child worker，自己只保留顺序控制和最终组装责任
- 每个 subagent 开工前都要先读：
  - `phase2-common-methodology.md`
  - `phase2-tech-file.md`
  - `phase2-mode-reference.md`（先选模式；选中后只读一个 `modes/*.md`）
  - 当前章节需要的 `../../autobid-office-tools/references/*.md`
- subagent 只处理自己负责的章节；如发现目录、标题或重编号判断需要调整，先回写技术章节树和 task store
- 只有范围已缩到叶子章节，或仅剩极小机械动作时，当前代理才可直接执行

## 技术文件的推荐大结构

技术文件常见地拆成两块：

- `（一）技术偏差表`
  处理逻辑与商务偏差表一致，只是把依据切换为技术条款、技术参数和限制条件
- `（二）专项投标文件`
  处理业绩、参数表、配置表、制造商说明、服务承诺、检测认证、人员资质和技术评分支撑等专项内容

如果招标文件已有明确的大标题，以招标文件为准；上面的拆法只是默认执行视角。

## 技术文件模板使用红线

技术文件模板不能直接套用。无论模板来自招标文件还是 `Data/modules/`，都至少检查：

- `模板标题`
  正式标题是否应保留，`XX格式 / XX模板 / 示例` 这类提示标题是否应删除
- `模板开头`
  开头说明、编制说明、适用范围、填写提示是否属于最终应提交内容
- `图片主体`
  大部分由图片/扫描件拼接出的 `DOCX`，优先直接拼接复用图片关系，不重做图片区
- `文本 / 表格`
  图片之外的文本和表格，必须逐项核对是否符合招标文件规定的格式与填写要求，该填写的内容必须填写

技术文件尤其不能犯这类错误：

- 只看模板文件名就直接套整章
- 保留了不该进入最终文件的模板提示标题
- 漏掉模板开头的正式说明文字或必需导语
- 对图片拼接模板重复重排，导致文件变形或失真
- 对文本和表格不做格式校验、不补项目字段就直接交付

## 技术文件章节填写规范

### 1. 技术偏差和参数响应章节

这类章节通常包括：

- 技术偏差表
- 技术规范响应表
- 参数符合性对照表
- 技术特性参数表
- 货物组件材料配置表

默认做法：

- `技术偏差表` 的处理逻辑与 `商务偏差表` 一致，先按 `招标要求 / 投标响应 / 偏差说明 / 证据位置` 建立响应结构
- 能表格化的优先表格化，不把参数响应写成长段叙述
- 不伪造客观参数，不用“完全满足”替代缺失的数据
- 对纯结论性的“是否满足要求”表述，若用户未另行否定且无反证，可直接按满足口径写明结论；但具体参数值、性能指标、图纸和测试数据仍不得猜写

对 `技术特性参数表`：

- 这不是“找到同名表格就复制”的任务，而是要先确认 `招标文件模板字段` 与 `技术规范书参数表` 的对应关系
- 先读取编制说明，确认是否要求把技术规范书中的 `技术特性参数表` 回填到投标文件模板
- 应按技术规范书中的对应参数逐项抽取、逐行填写，不得只摘一部分代表项
- 项目名称、单位等公开项应填写，但允许按可读性做智能分行，不把长字段硬挤在一行
- 招标人要求值应来自技术规范书原表
- `投标人保证值` 不是自由发挥项；若语义是投标承诺且无反证，默认直接与 `招标人要求值` 保持一致，表示投标人承诺满足要求
- 如果招标文件模板和技术规范书表头不完全同名，应按语义做字段映射后回填，而不是因为表头不一致就跳过
- 如果一张输出表实际对应技术规范书中的多张子表或多个分段，也要按输出表顺序合并回填

对 `货物组件材料配置表`：

- 这也不是“找到一张对应表就结束”的任务；要先确认输出表实际对应专用技术规范书中的哪些章节和哪些源表
- 允许从专用技术规范书中的多个源表抽取内容，再合并填写到一张输出表
- 当前这类表要特别注意：技术专项里实际可能分散为三张表，必须把三处内容都找齐后，再统一填入一张输出表
- `投标人响应的形式规格`、`数量` 默认与要求一致，其他无资料列可留空
- 必备但当前资料库没有的备品备件行，保留空行，不得因为无值而删行
- `必备的备品备件` 即使当前没有实际内容，也必须在输出表中保留该行，只是内容为空，不能省略
- 合并三张源表时，优先服从输出表的行序和字段结构，不机械保留源表原始分段外观

如果存在真实偏差，应明确写出：

- 偏差点是什么
- 对整体满足性的影响
- 是否需要用户确认

### 2. 业绩、授权和制造商说明章节

这类章节通常包括：

- 业绩文件
- 制造商授权委托书
- 制造商说明
- 其他专项证明

默认做法：

- 业绩文件通常按 `表格信息 + 贴图证明` 两段处理，信息表与贴图模板可分开维护，再按组装规则合并
- 业绩模板应先按产品类别选路由，再套对应模板；当前已知常见类别包括：
  - `智能巡视系统`
  - `变电站在线智能巡视系统`
  - `智能站辅助系统综合监控平台图像视频在线监测装置`
  - `视频在线监测装置`
  - `视频监视系统`
- 制造商授权委托书、制造商说明如果是“具备系统集成能力的制造商”场景，可保留固定能力描述，再按本项目补足标题、授权关系和必要说明
- `4.2 硬件产品（外购部件、零组件）生产商授权` 这类固定提醒段应保留
- 需要实时签订、实时更新的授权协议、合作协议和第三方函件，不由 AI 伪造正文，只保留提醒、挂载位置或真实附件入口
- 如果第一章投标人资格要求对报告、证书、授权材料有明确要求，必须回到资格要求和资料库核对，再挂对应模板或真实材料

### 3. 技术服务、售后、质量和制造工艺章节

这类章节通常包括：

- 技术服务
- 培训计划
- 安装指导
- 售后服务保障及承诺
- 质量保证措施方案
- 制造工艺

默认做法：

- `技术服务`、`培训`、`安装指导` 可以由 AI 生成，但必须同时受技术规范书和知识库约束，不自由发挥
- 服务类正文优先围绕 `对象 / 内容 / 方式 / 频次 / 响应时效 / 交付结果` 展开
- 售后服务、质量保证如已有成熟模板，优先复用 `module_docx` 或 `template_fill`
- 制造工艺类章节可在成熟模板基础上补充项目适配内容；如当前产品类别已有稳定模板，优先套模板再细修
- 所有承诺都要能落到可执行动作，不写纯宣传型话术

### 4. 生产能力、设备、人员、证书和报告章节

这类章节通常包括：

- 生产场地、生产能力及剩余产能列表、厂房面积
- 生产装备
- 调试试验场所、试验检测设备
- 认证证书
- 主要技术人员、项目经理及其相关证书
- 检测检验报告
- 资质业绩凭证单
- 投标主体承诺函

默认做法：

- 这类章节通常先填项目公开信息，再接固定模板、固定说明或扫描件挂载
- `生产能力及剩余产能列表` 如果模板是固定表格，通常只更新项目标题、时间安排和本项目日期，不重写整张表
- `生产装备`、`调试试验场所`、`认证证书`、`人员及证书` 这类章节优先做成“项目字段 + 固定资料挂载”的稳定模式
- 检测检验报告、证书、人员证照等材料优先挂真实资料，不主动解读敏感扫描件内容
- `资质业绩凭证单（如有）` 要按分标或包号对应提供，不能跨分标混挂

### 5. 技术评分支撑章节

这类章节通常对应：

- 招标文件中的 `技术评分标准` 条款
- 技术能力、方案能力、案例能力等得分支撑材料

默认做法：

- 先读取第一阶段产出的技术评分细则
- 技术评分支撑优先做成一张或一组映射表，不重复堆放整份支撑材料
- 表格至少回答四件事：
  - 评分项是什么
  - 响应结论是什么
  - 支撑材料是什么
  - 材料在技术文件的哪个章节位置
- 如果支撑材料已在技术文件正文其他章节出现，这里优先写映射位置，不重复贴整批图片

技术评分支撑不应脱离评分标准自由发挥，而应让评委能够快速看到“这个点为什么能得分、去哪里核对”。

## 技术文件的常用模式映射

可优先按以下语义选模式：

- `技术偏差表 / 参数响应表` -> `table_fill`
- `技术特性参数表 / 货物组件材料配置表` -> `table_fill`
- `业绩文件（信息表 + 贴图）` -> `group_assembled`
- `按规则生成的技术说明 / 制造商说明 / 技术服务` -> `rule_generated`
- `售后服务 / 质量保证 / 成熟技术整章模板` -> `module_docx`
- `检测报告 / 认证证书 / 人员证书 / 说明书截图` -> `fixed_shell_image`
- `技术评分点分组章节` -> `group_assembled`
- `因项目不适用而不提交的章节` -> `conditional_ignore`

各模式的标准动作和特殊说明不要在技术文件入口一次性加载。先读 `phase2-mode-reference.md` 选模式，再只读对应文件：

- `table_fill` -> `modes/table-fill.md`
- `fixed_shell_image` -> `modes/fixed-shell-image.md`
- `module_docx` -> `modes/module-docx.md`
- `rule_generated` -> `modes/rule-generated.md`
- `group_assembled` -> `modes/group-assembled.md`
- `conditional_ignore` -> `modes/conditional-ignore.md`

## 技术文件特有注意事项

- 技术文件要优先对齐技术条款和评分点，不要脱离招标要求自说自话
- 对“满足要求”的证明，优先给出结论 + 参数 / 方案依据 + 证据位置
- 对“争取得分”的说明，优先突出评审要素对应的能力和材料，不要把案例、证书、图纸散乱堆放
- 技术方案类章节应避免营销话术和无证据的绝对化表达
- 需要用户补充的技术数据、图纸、截图、业绩细节，应显式留槽位，不自动猜写；但对纯满足性判断不默认制造 `用户填写` 槽位
- `投标人保证值` 这类承诺字段可按满足口径写成与招标要求一致，但不能借此补写客观检测数据
- 项目信息、单位信息等长字段应优先保证成稿可读性，必要时主动分行
- 同一章既要表格又要贴图时，优先拆成 `信息表 partial + 贴图 partial`，最后统一组装
- 技术服务、培训、制造工艺等 AI 生成章节，应以技术规范书、知识库和企业现有模板为上限，不越界编造

## 必须回写的技术元数据

至少回写：

- 技术文件源章节结构
- 技术文件输出章节模板
- 关键条款与评分点映射
- 每章采用的处理模式
- 主要引用来源和所挂材料
- 需人工确认的技术参数和待补资料
