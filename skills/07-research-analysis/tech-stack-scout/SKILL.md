# Tech Stack Scout — 技术栈调研

## 一、核心原则

**需求先于搜索**。不先澄清约束条件，所有的搜索都是在做无效的普适性对比。
你的技术栈、团队能力、部署环境，会直接否掉 80% 的"通用最佳实践"。

---

## 二、调研流程

### Phase 0：需求锁定（搜索前必做）

在任何搜索之前，先回答（如果用户没提，逐一确认）：

```
□ 我要解决的核心问题是什么？（一句话描述）
□ 现有技术栈是什么？（不能引入的依赖？）
□ 部署环境约束？（本地 / 云 / 私有化 / 离线）
□ 性能要求？（QPS / 延迟 / 数据量级）
□ 团队熟悉度？（学习成本可以有多高？）
□ 时间约束？（需要多快跑起来）
□ 硬性淘汰条件？（许可证 / 语言限制 / 合规 / 运行环境）
```

> 如果这些信息不完整，**先问，再搜**。不要带着模糊需求开始调研。

---

### Phase 0.5：问题改写（禁止只搜产品名）

基于 `associative-research` 的概念地图，至少生成这 4 类查询：

```markdown
1. 问题导向：我到底在解决什么工程问题？
2. 机制导向：这个问题通常由什么技术机制解决？
3. 失败导向：现有方案最常见的坑是什么？
4. 迁移导向：别人从什么迁移到什么，为什么迁移？
```

不用写复杂日志，但要避免后面退化成 `"X vs Y"` 复读。

---

### Phase 1：候选方案识别

**第一步：直搜主流选项**（3-5 个足够）

**第二步：调用 associative-research 的跳跃策略找非主流**

技术调研特有的跳跃路径：

| 策略 | 操作 | 示例 |
|------|------|------|
| 搜「反对意见」 | "为什么不用 X" / "X 的问题" / "从 X 迁移到" | 找到 X 的真实缺陷 |
| 搜生产案例 | "[方案名] production / at scale / lessons learned" | 找真实踩坑经验 |
| 搜 issue tracker | GitHub issues: "performance" / "memory leak" / "breaking change" | 找已知 bug 和维护质量 |
| 搜替代品讨论 | "X vs" / "X alternative" / "X replacement" | 可能发现你没预期的候选 |
| 搜上游依赖 | 看它依赖什么库，那些库有没有独立方案 | 可能直接用底层更合适 |

**第三步：蛛丝马迹追踪**

调研技术时特别关注这些意外信号：
- 搜索结果里出现了一个你没见过的项目名，但描述和你的需求高度吻合
- 某个 issue 里有人说"我们用 XXX 替代了它，效果更好"
- 某篇博客文章批评主流方案，并推荐了一个冷门替代

---

### Phase 2：多维评估

> 维度不固定，根据 Phase 0 的约束条件动态生成。以下是基础维度，按需增删。

```
□ 功能匹配度：能不能解决我的核心问题？（有没有关键功能缺失？）
□ 与现有栈的兼容性：能否无缝集成，还是需要大改？
□ 性能基准：是否有公开的 benchmark，或生产案例支持？
□ 维护活跃度：最近 commit 时间 / issue 响应速度 / star 趋势
□ 学习成本：文档质量 / 社区规模 / 中文资源
□ 生产可靠性：有没有大规模使用案例？有没有已知的稳定性问题？
□ 已知坑：GitHub issues / 社区讨论里的高频 pain point
□ 版本风险：有没有 breaking change 历史？维护者是否活跃？
```

---

### Phase 2.5：轻量校验

对重点候选，至少顺手看三样东西：

- 官方材料：它自己怎么定义功能和边界
- 批评性材料：issue、迁移文、"为什么不用 X"
- 近期信号：最近 release / discussion 有没有明显变化

如果桌面调研仍难分胜负，就把争议点留给 POC，不要硬编结论。

---

### Phase 3：结论生成

结论格式（固定，不能跳过任何一项）：

```markdown
## 推荐

**首选：[方案名]**
理由：[3 条以内，每条对应一个约束条件]
主要风险：[1-2 条，不能回避]

**次选：[方案名]**（适用条件：[XXX 时才考虑]）

## 明确排除

| 方案 | 排除原因 |
|------|---------|
| X | [具体原因，而不是"不够流行"] |
| Y | [具体原因] |

## 待验证

（调研中发现但没有充分证据的结论，需要 POC 验证的点）
```

## 三、反模式

**反模式 1：用 star 数量排名决定选型**
- 症状：选 star 最多的，或"大厂用 X 所以用 X"
- 后果：大厂的约束条件和你完全不同
- 修复：回到 Phase 0，把你自己的约束条件作为核心筛选标准

**反模式 2：只看官方文档**
- 症状：调研报告全是官方特性列表，没有任何 tradeoff
- 后果：没有发现真实的坑
- 修复：必须包含至少一个「批评性来源」（issue / 迁移博客 / 对比文章）

**反模式 3：版本快照陷阱**
- 症状：引用一篇 2022 年的对比文章做结论
- 后果：技术栈变化很快，结论可能已经失效
- 修复：标注信息来源时间；对关键结论用最新 issue/release 验证

**反模式 4：把 benchmark 当成最终裁决**
- 症状：看到某篇 benchmark 领先，就直接判定技术胜出
- 后果：忽略了数据分布、运行条件、维护复杂度和稳定性
- 修复：必须用真实使用材料和批评性来源交叉验证 benchmark 结论
