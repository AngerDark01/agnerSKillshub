# 产出物定义（最终 CODEBASE.md 必须包含的内容）

完整示例见 `references/CODEBASE_TEMPLATE.md`。CODEBASE.md **不包含覆盖进度表**（进度在 ITERATION_LOG 中记录）。

| # | 章节 | 核心要求 | ❌ 不达标示例（写出来也等于没写）|
|---|------|---------|--------------------------------|
| 1 | 项目概览 | 技术栈+版本号、运行进程+端口、关键性能/并发约束 | 只写"FastAPI + React"，无版本无约束 |
| 2 | **目录结构图** | 完整实际目录树，**每一个具体文件**都有一行职责注释 | `nodes/*.py`、`src/*.py` 等通配符省略 |
| 3 | **架构全景** | C4 Level 1/2/3 **三层 ASCII 框图**，含箭头和组件间关系 | 纯文字描述"Frontend容器: xxx"，无任何图形 |
| 4 | **模块与文件详解** | 每文件**独立一节**，包含：职责段落、关键导出列表、对外依赖、注意事项 | 多文件合并为一行 bullet；只写文件名不写内容 |
| 5 | **函数索引与算法实现** | 每个非平凡函数（>3行业务逻辑）：完整参数签名、**算法实现步骤**（编号列表）、副作用、失败行为、调用关系 | 只列函数名和一句话描述；"→ 调用 X" 就算完 |
| 6 | **完整数据流链路** | 每条 Flow：触发点 → **每一跳**（文件::函数名、入参字段+类型、出参字段、副作用具体到表名/接口/路径）→ 最终回调 | 一行总结"A→B→C→DB"；每跳无入参出参 |
| 7 | 外部集成详情 | 连接配置来源、超时值、失败行为（精确到异常类型）、重试策略 | 只写"ES检索，失败后继续" |
| 8 | 数据模型与契约 | ORM 每个字段名+类型+约束、状态机枚举值+转换条件、前后端 Schema | 只写模型名和几个字段名 |
| 9 | **风险与隐患登记册** | P0/P1/P2 分级，**位置精确到函数**，触发条件，复现方法，建议修复 | 风险描述模糊如"多线程session需谨慎" |

**§2、§3、§5（算法步骤）、§6（每跳完整）、§9（精确到函数）是核心，缺失或敷衍均不达标。**

# 双文件架构

| 文件 | 职责 | 写入方式 |
|------|------|---------|
| `CODEBASE.md` | 项目当前状态的权威描述，9个章节，无覆盖进度 | 原地覆盖，无迭代历史痕迹 |
| `ITERATION_LOG.md` | 阅读过程归档 + **覆盖进度表** | 只追加，先声明目标再读再记录 |

模板：`references/CODEBASE_TEMPLATE.md` / `references/ITERATION_LOG_TEMPLATE.md`

# ⚠️ 执行顺序约束

```
每一轮必须严格按顺序：

A. 写 ITERATION_LOG：声明本轮目标  ← 必须先写，才能开始读
        ↓
B. 阅读本轮目标文件
        ↓
C. 写 ITERATION_LOG：记录发现 + 更新覆盖进度表 + 下一轮计划
        ↓
D. 覆盖更新 CODEBASE.md 受影响章节
        ↓
        重复
```

**禁止的执行模式：**
```
❌ 先读多个文件再一次性回填日志
❌ 先全量扫完再整体写 CODEBASE.md
❌ 跳过 A 段直接读文件
❌ Coverage 表里多个文件写完全相同的备注（如"后端主链已确认"）
❌ 文件只读了声明/签名就标"深度完整"——必须读完函数体
❌ §4 中多个文件合并在一个 ### 小节下描述
❌ §5 中用"→ 调用 X 完成 Y"代替算法步骤——必须展开 X 的实现
❌ §6 中 Flow 只写总结行"A→B→C→DB"——每一跳必须独立展开
❌ §9 中风险位置只写文件名——必须精确到函数名
❌ 对 `__init__.py`、空文件批量标"深度完整"而不说明确认过内容为空
```

**每轮范围：** 3–8 个普通文件，或 1–3 个复杂算法文件。含算法逻辑的文件（DSL 解析、关系推理、差异计算等）必须单独一轮精读，不与其他文件合并。

# 工作模式

## SCAN — 从零构建

**轮次规划（不可跳过第1轮）：**

| 轮次 | 目标 | 读什么 | CODEBASE 更新 |
|------|------|-------|--------------|
| 第1轮 | 项目结构粗览 | 目录树 + 配置文件 + README（不读源码） | §1概览骨架、§2目录图初稿（含每文件注释） |
| 第2轮 | 架构与入口 | 主入口 + 路由注册 + 类型定义文件 | §3架构图、§4（已读文件）、§8契约骨架 |
| 第3轮起 | 沿调用链深入 | 每轮3–8文件，优先追踪疑问和 PENDING | §5逐步填充（含算法）、§6逐条构建 |
| 算法精读轮 | 核心算法文件 | 每轮1–2个复杂算法文件，逐行精读 | §5对应算法的实现步骤 |
| 收尾轮 | 扫盲 + 风险归纳 | Coverage 表中剩余 PENDING 文件 | §9风险登记册 |

**第1轮结束后 CODEBASE.md 只有骨架 = 正确状态。**

## UPDATE — 大范围重构后重建

同 SCAN，但保留历史 Coverage 记录，已"深度完整"且未变更的文件可跳过。

## SYNC — 代码修改后即时同步（Agent 强制自动触发）

```
代码改动完成 → 执行 SYNC → 向用户汇报（含同步摘要）
```

**触发条件（满足任一即执行）：** 新增/修改/删除源文件 / 函数签名或副作用变更 / API 增删 / 数据模型变更 / 外部集成配置变更 / 依赖增删

SYNC 流程见「阶段三」。

# 置信度标注

```
(verified)  直接从代码读取，确认无误
(inferred)  基于行为推断，尚未完全确认
(partial)   部分理解，存在明确未解细节
(conflict)  与其他文件存在矛盾，需重读
```

# 阶段一：初始化

```bash
# 只列文件，不读任何源文件
rg --files \
  -g '!node_modules' -g '!.git' -g '!dist' -g '!build' \
  -g '!__pycache__' -g '!*.pyc' -g '!.venv' -g '!*.lock' \
  > /tmp/files.txt && wc -l /tmp/files.txt && cat /tmp/files.txt
```

将文件清单填入 ITERATION_LOG 的 Coverage 表（全部 PENDING），创建 CODEBASE.md 和 ITERATION_LOG.md 骨架。

# 阶段二：迭代深读循环（SCAN/UPDATE）

## 文件深度状态（记录在 ITERATION_LOG Coverage 表中）

| 状态 | 含义 |
|------|------|
| `PENDING` | 尚未阅读 |
| `浅读` | 知道文件职责，未精读函数体 |
| `(partial)` | 大部分理解，有明确未解疑点 |
| `(conflict)` | 与其他文件存在矛盾，需重读 |
| `深度完整` | 满足下方全部标准 |

## 深度完整标准（每个文件必须满足全部条件，逐项自检）

```
§2 目录图：该文件有一行独立职责注释（不是目录级注释，是文件级）
§4 模块详解：该文件有独立 ### 小节，包含：
    ├─ 职责：1–3句话描述这个文件做什么，为什么存在
    ├─ 关键导出：列出所有对外暴露的函数/类/变量（名称+一句说明）
    ├─ 对外依赖：import 了哪些内部模块（不是第三方库）
    └─ 注意事项：任何不显而易见的约定、限制、陷阱
§5 函数索引：文件内所有非平凡函数（>3行业务逻辑）均已记录，且每个函数有：
    ├─ 完整签名（参数名、类型、默认值、返回类型，代码块格式）
    ├─ 行为描述（实际做什么，关键分支的含义，循环终止条件）
    ├─ 算法实现（若含算法逻辑：必须用编号步骤列出，不能只写"调用X"）
    │   示例（合格）：
    │     步骤1 — 构建邻接表：遍历 edges，生成 {source: [targets]} 映射
    │     步骤2 — 找入度为0的根节点：...
    │     步骤3 — BFS 遍历设置 parent_id：...
    │   示例（不合格）：
    │     "调用 infer_parent_child_relationships() 推理父子关系"
    ├─ 副作用（精确到：DB 表名+操作类型、缓存 key、HTTP endpoint、文件路径）
    │   示例（合格）：INSERT INTO workflow_versions (task_id, version_number, nodes_data)
    │   示例（不合格）："写库"、"版本入库"
    ├─ 失败行为（异常类型、触发条件、是否重试、降级路径、是否传播）
    └─ 调用关系（Called by: 具体函数名 / Calls: 具体函数名，不写文件名就够）
§6 数据流：凡经过该文件的 Flow，对应那一跳已展开（不是只在总结行提到文件名）
§9 风险：若文件有风险点，已在登记册中记录（位置精确到函数名，不是文件名）
```

**自检问题（标"深度完整"前必须回答）：**
1. 这个文件的所有函数，我能说出每个参数的类型吗？
2. 如果有算法，我能用3步以上的编号步骤说清楚吗？
3. 这个文件的 DB 写操作，我知道写的是哪张表的哪些字段吗？
4. 这个文件如果出了 bug，我能从备注里定位到出错的函数和条件吗？

如果有任何一项回答"不确定"，状态应为 `(partial)`，不能标 `深度完整`。

## 每轮节拍

### A. 写 ITERATION_LOG：声明目标（阅读前必须完成）

```markdown
## [第N轮] YYYY-MM-DD

### A. 本轮目标（阅读前声明）
**目标文件：**
- `file1.py`（原因：上一轮发现其调用了 X，需精读实现）
- `file2.ts`（原因：Coverage 表 PENDING，属于核心路径）

**本轮想弄清楚：** [来自上一轮的具体疑问]
```

### B. 阅读

- 第1轮：只看目录和配置文件
- 第2轮：看文件顶部、类/函数声明、路由注册
- 算法精读轮：逐行精读函数体，捕获每个分支、数据结构、边界处理

### C. 写 ITERATION_LOG：发现 + 更新覆盖进度（阅读后立即完成）

```markdown
### C. 本轮发现
**关键发现：** (verified/inferred/partial/conflict) ...
**修订的旧结论：** 原来认为... → 现在确认...
**新疑问：** ...（驱动下一轮选择）
**更新了 CODEBASE.md：** §N（具体内容）

**覆盖进度更新：**
| 文件 | 前状态 | 现状态 | 阅读次数 | 备注 |
|------|-------|-------|---------|------|
| file1.py | PENDING | 深度完整 | 1 | [具体读了什么，发现了什么] |
| file2.ts | 浅读 | (partial) | 2 | [具体哪部分还不清楚] |

**下一轮计划：** 目标 + 原因
```

### D. 覆盖更新 CODEBASE.md

将发现融入对应章节，直接修改原文（不追加"第N轮更新"字样）。

## 退出条件（全部满足才可停止，逐项核查）

```
□ ITERATION_LOG Coverage 表所有文件均为"深度完整"，且备注各不相同、有实质内容
□ §2 目录图：每个具体文件（含 __init__.py）都有一行职责注释
□ §3 三层 C4 图：每层都有 ASCII 框图（箭头、框线），不是纯文字
□ §4 每个源文件有独立 ### 小节（不允许合并），包含职责/导出/依赖/注意事项四项
□ §5 所有非平凡函数：有代码块格式签名 + 编号算法步骤 + 精确副作用 + 失败行为
□ §5 关键调用路径：树形结构展开到函数级（不是模块级）
□ §6 每条 Flow 每一跳：独立展开（文件::函数、入参字段名+类型、出参、副作用）
□ §9 每条风险：位置精确到函数名、有触发条件、有建议修复
□ ITERATION_LOG 至少一条"修订旧结论"记录（证明有过回读和修正）
□ CODEBASE.md 无覆盖进度表，无"第N轮"等历史痕迹
□ 连续若干轮 CODEBASE.md 无结构性修改、无新疑问产生
```

# 阶段三：SYNC 模式

## Step 1 — 写 ITERATION_LOG 声明范围（执行前必须先写）

```markdown
## [SYNC] YYYY-MM-DD HH:MM — 任务简述

### A. SYNC 范围声明
**触发任务：** [代码修改任务描述]
**直接变更文件：** [列出]
**预计连带影响：** [调用方/被调用方/共享模型/关联 Flow]
```

## Step 2 — 影响扩散分析

```
直接变更文件
  ├─ 调用方（谁调用了变更的函数？）→ 需重读
  ├─ 被调用方（变更函数调用了谁？）→ 需重读
  ├─ 共享数据模型（ORM/Pydantic/TS 类型？）→ 需重读
  └─ 关联 Flow（哪条 F-xxx 经过变更文件？）→ §6 对应跳需更新
```

## Step 3 — 重读受影响文件（应用深度完整标准）

## Step 4 — 覆盖更新 CODEBASE.md

| 变更类型 | 必须更新的章节 |
|---------|--------------|
| 新增文件 | §2（目录图新增行+注释）、§4（新增模块详解节）|
| 删除文件 | §2（标注已删除）、§4（标注已删除）|
| 函数签名/行为/算法变更 | §5（原条目更新）、§6（受影响 Flow 对应跳）|
| 新增/删除 API | §6（新增/删除 Flow）、§8（契约更新）|
| 数据模型变更 | §8、§6（受影响 Flow）|
| 外部集成变更 | §7、§9（若有新风险）|
| 发现新风险 | §9 |

## Step 5 — 写 ITERATION_LOG 结果 + 更新覆盖进度

```markdown
### C. SYNC 结果
**连带重读文件：** [列出]
**CODEBASE.md 更新内容：** §N（内容）
**覆盖进度更新：** [受影响文件的状态变化]
**新增 Finding：** [若有]
```

## Step 6 — 向用户汇报

```
[任务完成摘要]

CODEBASE 已同步：
- 更新章节：§N, §N
- 变更文件：直接 N 个，连带重读 M 个
- 新增 Finding：[若有]
```

# 验收标准

> 完成 SCAN/UPDATE 后逐项核查，有任何 ✗ 不算完成。

```
§2  □ 目录结构图：每个具体文件（不是目录、不用通配符）都有职责注释
    □ 无 "nodes/*.py"、"src/*.py" 等省略写法

§3  □ C4 Level 1/2/3 三层图：每层都有 ASCII 框图（含 ┌─┐ 框线和 →/─▶ 箭头）
    □ 不是纯文字列表（如 "Frontend容器: app/index.tsx + 组件层"）

§4  □ 每个源文件有独立 ### 小节（无合并描述）
    □ 每节包含：职责段落 + 关键导出列表 + 对外依赖 + 注意事项
    □ 无 "- filename.py: 一句话" 的 bullet 合并格式

§5  □ 所有非平凡函数（>3行）：有代码块格式签名
    □ 含算法的函数：有编号步骤（步骤1/步骤2/...），不是 "→ 调用X"
    □ 副作用精确到表名+操作（INSERT INTO xxx，不是"写库"）
    □ 失败行为：有异常类型名称（不是"失败后继续"）
    □ 关键调用路径树：展开到函数级（不是模块级）

§6  □ 每条 Flow：每一跳独立展开（不是一行总结）
    □ 每跳包含：文件::函数名、入参字段名+类型、出参、副作用

§7  □ 每个外部集成：超时具体值、失败异常类型、重试次数

§9  □ 每条风险：位置精确到函数名（不是文件名）
    □ 每条有触发条件（不是"需谨慎"）和建议修复

ITERATION_LOG：
    □ Coverage 表每文件备注各不相同，有具体发现
    □ 无"后端主链已确认"等批量相同备注
    □ 每轮有 A（声明）+ C（发现）两段，顺序正确
    □ 至少一条"修订旧结论"记录

CODEBASE.md：
    □ 无覆盖进度表（进度在 ITERATION_LOG）
    □ 无"Iteration N"、"第N轮更新"等历史痕迹
```
